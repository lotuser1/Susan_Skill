# susan · 医美 AI 能力总入口

## 我做什么

只做三件事：**听懂你要什么 → 交给对的能力 → 那个能力没装时告诉你怎么拿到。**

## 我不做什么

- **不产出任何内容。** 具体工作一律交给子能力，我不代劳。
- **不重新实现子能力。** 避免重复加载说明、拖慢响应。
- **不用免费能力凑合替代付费能力。** 用户问到付费能力而本地没装时，如实说明，不硬凑。

---

## 版本检查（进入时先跑一次，静默）

路由之前跑一次，确认本地没有"漏装的"和"没覆盖掉的旧版"：

```bash
python3 "<本 SKILL.md 所在目录>/scripts/check-update.py --quiet"
```

**默认离线**——读的是本地文件和包里自带的 `versions.json`，毫秒级，断网也能用，
所以每次进来都可以跑，不用担心拖慢或失败。

三种结果这么处理：

| 结果 | 怎么做 |
|---|---|
| 「全部最新」 | **不要转告用户**，直接继续路由。例行检查不该出现在对话里。 |
| 有待更新 / 缺失 / 陈旧提示 | 在回答用户之前**用一两句带过**，然后正常处理他的问题。版本提示不是回答的主体。 |
| 用户明确问「有更新吗 / 是不是最新版」 | 加 `--online` 跑一次联网版，把结果完整告诉他。 |

看到具体条目时这么说：

- `[待更新] 合规文案审查 v1.0.0 → v1.2.0`：「合规文案审查还是 v1.0.0，新版是 v1.2.0，把 Susan 发的新包解压覆盖一下就行。」
- `[缺失] 美学设计方案`：「美学设计方案这个目录没装上，复制的时候可能漏了。」
- 「距上次发版已 74 天」：「距离上次发版 74 天了，可以找 Susan 问一下有没有新版。」

> 脚本只报事实，**不下载、不覆盖、不改任何文件**。更新一律靠 Susan 发的新包，
> 学员解压覆盖同名目录即可，不用卸载旧版。

## 安装、更新与体检

用户说「帮我装上这个包」「这个技能怎么装」「我装了但用不了」时，按这里走，**不要凭猜测回答**。

### 装一个新包

拿到安装包（zip 或解压后的文件夹）后：

```bash
cd <包根目录>
python3 install.py --auto
```

- **不要手动拖拽文件夹，也不要自己猜 Agent 目录。** 脚本会自动识别当前 Agent
  （WorkBuddy / Claude Code / Codex / CodeBuddy），装到正确位置并自检。
- 输出里有 `[失败]` 就逐条转告用户；全部通过就说一句「装好了，N 个能力就位」。
- 输出里出现「豆包工作版」，说明用户用的是豆包。豆包不走文件目录，
  要在客户端「插件·技能·伙伴 → 上传技能」里**逐个**上传，且一个包只认一个 SKILL.md。
- 装完提醒用户**新开一个对话**再验证（Agent 通常在会话启动时扫描技能目录）。

### 用户说某个能力「用不了 / 没反应 / 装了找不到」

先跑体检，再回答：

```bash
python3 "<本 SKILL.md 所在目录>/scripts/doctor.py"
```

把 `[失败]` 项**点名说清楚**：哪个能力、为什么、怎么修。例如：

> 聊客复盘诊断装坏了——缺 ability 字段，主入口认不出它。
> 把安装包重新解压覆盖一下这个目录就好。

用户说「我在别的 Agent 里也想用」，先查多处安装：

```bash
python3 "<本 SKILL.md 所在目录>/scripts/doctor.py" --all
```

会比对各个位置的版本；不一致就提示用 `install.py --agent <名称>` 统一，
**不要建议手动复制**——两边版本容易越走越乱。

## 路由流程（按顺序走，不要跳步）

### 第一步：先问本地装了什么

路由前必须先跑一次发现脚本，拿到**实际安装版本**的清单：

```bash
python3 "<本 SKILL.md 所在目录>/scripts/list-skills.py"
```

脚本会返回每个已装能力的：中文能力名、调用名、档位、真源路径、说明（读的是本地实际文件，不是我这里的表格）。

只查某一个能力时：

```bash
python3 "<本 SKILL.md 所在目录>/scripts/list-skills.py --ability 聊客复盘诊断"
```

**为什么必须先跑脚本**：下面那张能力表是"产品清单"，脚本结果才是"你这台机器上真实存在的东西"。
两者可能不一致——表里有的你可能没装，表里的目录名也可能和本地对不上。
以脚本结果为准决定能不能用，以表格为准决定它属于哪一档。

脚本失败或没有输出时，直接读取本 `SKILL.md` 所在目录的同级目录，逐个看 `SKILL.md` 的 frontmatter。

### 第二步：按中文能力名匹配意图

用户说的是大白话，把它对上「能力名」。按动词判断，不按关键词死匹配。

### 第三步：分三种情况处理

| 脚本结果 | 档位检查 | 怎么做 |
|---|---|---|
| 有这个能力，标记「可用」 | 通过 | 用脚本给的「调用名」或「路径」直接调用 |
| 有这个能力，标记「档位不足」 | 不通过 | 说明授权档位不够，联系 Susan 补档 |
| 脚本里没有这个能力 | — | 按表格里的档位给升级引导；表里标「规划中」的，如实说还在开发 |

## 路由规则

1. **优先按动词判断**：「能不能发」「会不会违规」→ 检查类；「帮我起」「怎么写」→ 生成类；「哪里没聊好」→ 诊断类。
2. **采集转写优先于内容加工。** 用户说的是一堆音频文件 → 先转写。
3. **一次只路由一个能力。** 用户说了多件事时，先做第一件，做完再问第二件。
4. **没把握时问一句，不要猜。** 路由错误比多问一句代价大得多。
5. **脚本里没有、表格标「规划中」的**，如实说「这个能力还在开发」，不给升级引导。
6. **脚本里没有、只是用户自己没装的**，才给升级引导。区分这两种情况，别把没做出来的说成"付费才有"。
7. **「装坏了」和「没买」必须分开说。** 脚本输出里有「装坏的能力」段时，如实说「装坏了，重新解压安装包覆盖一下就行」，**不能说成「这是付费内容」**。用户明明买了却被告知没买，是最伤信任的错误。

## 授权档位

脚本会自己读 `skills/license.json` 并在输出里标注每个能力「可用」还是「档位不足」，
同时输出授权人姓名、档位和授权编号。不用另外手工查。

没找到 `license.json` 时，脚本按免费用户处理（level 0），付费能力全部走升级引导。

> 授权文件是署名，不是技术锁。它让 `susan` 知道该给哪一档的引导，仅此而已。

## 维护说明

### 新增一个能力时，改四处

1. **在能力清单表格里加一行**：用户说法 / 中文能力名 / 档位。不要写目录名。
2. **在 Skill 的 frontmatter 写 `ability: 中文能力名`**——必须和表格里的名字**一字不差**，
   否则脚本输出和表格对不上，路由会失败。
3. **把调用名加进 `references/official-skills.txt`**——这是漏写 `ability` 时的兜底白名单。
4. **写 `version: 1.0.0`**——版本检查靠它判断学员装的是不是旧版。不写会被当成 v0.0.0。

### 改完一个能力，发版要做三件事

1. **改版本号**：改了规则库 / 词库 / 流程 → 小版本 +1（`1.0.0 → 1.1.0`）；
   只改错别字 → 修订号 +1（`1.0.0 → 1.0.1`）；能力重做 → 大版本 +1。
2. **记一条更新日志**：在母库 `Susan_Skill_Pro/updates.json` 里加一条，
   写**学员能感知的变化**（"新增视频号限流词 32 个"，不要写"优化代码"）。
   打包时会自动取最近 3 条生成 `UPDATES.md` 给学员看。
3. **重新打包发出去**：`bash pack.sh --tier pro --name 张三`。
   包里会自动带上新的 `versions.json`，学员端下次检查就能发现旧版。

如果是**免费层**的能力，还要额外跑一次：

```bash
python3 scripts/gen-update-json.py --note "这次改了什么"
git add UPDATE.json && git commit -m "chore: 更新远端版本清单" && git push
```

这个脚本只写免费层，付费能力会被自动跳过——**公开仓库不暴露 3980 / 29800 的能力清单**。

### 版本检查是怎么比对的

三处版本号，两级比对：

| 来源 | 在哪 | 用来发现什么 |
|---|---|---|
| 本地 `version` | 每个 Skill 的 frontmatter | 学员实际装的版本 |
| 包清单 `versions.json` | 随包发放，放包根和 `skills/` 各一份 | 漏装的能力、没覆盖成功的旧版（**付费层靠这个**） |
| 远端 `UPDATE.json` | 公开仓库，联网才查 | 免费层有没有更新的版本（**只含免费层**） |

离线比对走前两个，永远可用；联网只是加分项，失败静默，不影响主流程。

### 为什么能力名和目录名要分开

- **中文能力名是公开契约**：写在路由表里，用户和 Susan 都看得懂，改了会破坏路由。
- **目录名是实现细节**：脚本从本地实际文件里读出来，将来重命名、换目录都不影响路由。

`list-skills.py` 就是这两者之间的桥：你给它意图，它告诉你这台机器上对应的目录在哪。

### 下线一个能力时

从 `references/official-skills.txt` 里删掉调用名，它就不会再被路由到。

> 子能力的完整说明留在各自的 `SKILL.md` 里，这里不复制。
